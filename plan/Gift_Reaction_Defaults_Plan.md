# 送禮／餵食反應：解除抑制計畫

> 初稿：2026-09-04（v1 雙軸強制版，已作廢）
> 改稿：2026-09-04（v2 解除抑制版）
> 再改：2026-09-04（v3 本版：補上「明示允許省略」與「明示允許即興」兩條）
> 狀態：設計定案，尚未實作
> 基準版本：v2.31.0（`4e584e1`）
> 直接前置：`89a45e4 fix(gift): let gift reactions see the conversation they happen in`

## 1. 判準

先確立驗收標準，因為前兩版計畫錯在這裡。

**合乎當下對話情境 > 涵蓋指定內容。**

實例（使用者提供）：

| 訪客 | 合格的回應 | 說明 |
|---|---|---|
| 「你中午吃飯了沒，我這有布丁，給你吧」 | 「謝謝，我剛好沒吃飯」<br>「我有吃飯，不過正好拿來當甜點」 | 對話的重心是有沒有吃飯。**這時去評論布丁好不好吃反而多餘** |
| 「我點到一本魔導書送你吧，但我不知道內容是啥」 | 「謝謝，我看這應該是古代魔法的書」<br>「謝謝，我來研究一下」 | **兩者都自然。** 說不說出內容不該由規則決定 |

後續追問（「剛剛的布丁好吃嗎？」「魔導書你研究之後是什麼書？」）必須接得下去。**她用掰的也可以**——訪客不會知道上次抽到什麼 variant。記得住更好，但不是必要條件。

## 2. 前兩版計畫錯在哪

v1 把「她沒說出書名」診斷成「缺少強制條款」，於是加了一條強制條款；為了讓強制條款在食物上成立，又得拆分客觀／主觀事實；為了保證每次抽籤都含觀察成分，又得把 `reactions` 改成雙軸 schema，連帶兩個新函式、正規化器、4 個測試、smoke test 與文件。

整條鏈的根都是那條強制條款。依 §1 的判準它是錯的——它會逼出「多餘的布丁評論」。**強制條款一撤，整條鏈全部倒掉。**

保留的只有一個判斷：昨天的改動確實造成了抑制。但解法是**解除抑制**，不是**換一條相反方向的強制**。

## 3. 關鍵洞察：不要把「要不要動手」提成待決問題

`89a45e4` 寫進 items.json 的是：

```
実際にこの場で開くかどうかは、この回の会話が決める。
```

問題不在於它是條件句，而在於它把「是否執行一個有代價的動作」（拆開別人送的禮物）提成了一個需要模型裁決的問題。面對這種問題，模型一律選安全的那邊——不開，於是也沒得說。

因此**換一個條件句沒有用**（「口をつけるかどうかは会話の流れによる」會以完全相同的方式失敗）。

有效的做法是不要提出這個問題：把印象寫成她**已經取得**的狀態，說不說由對話決定。取得印象是廉價的、不需要裁決；要不要講出來則高度依賴語境，而那正是模型擅長的。

這條原則同時解釋了 §1 兩個魔導書答案為何都自然：兩者都不需要她先裁決要不要開。

**但「不提出問題」本身還不夠。** 現行規則沒有任何一句告訴模型「這些你可以不講」。在缺乏明示許可時，模型會把列出來的每一項都當成應盡義務，於是即使拿掉強制條款，也可能繼續每次都把味道、內容、道謝、動作全部交代一遍——那正是 §1 布丁例子判定為不通過的形狀。

因此 v3 補上兩條**明示許可**（v2 缺）：

1. **允許省略**：味道、內容、道謝、動作不必每次全部說明。
2. **允許即興**：對話尚未確定的細節，可在不與已說出口的內容矛盾的前提下自然補足。

第 2 條同時取代了 v1 §3.1 那張「客觀／主觀事實」拆分表——當時需要整套管轄拆分才能讓她合法描述味道，一句明示許可就夠了。

## 5. 要改的三處

### 5.1 `ghost/Frieren/items.json` — 拿掉待決問題

**魔導書**

```json
"prompt": "相手が魔導書を差し出した。魔導書はフリーレンが特に喜ぶ贈り物である。数頁を繰れば{variant}らしいと見て取れる品である。相手が中身を承知の上で選んだとは限らない。"
```

- 刪掉「実際にこの場で開くかどうかは、この回の会話が決める。」——**這一句才是病灶**（§3）
- v2 寫成「手に取って数頁を繰ってみると」是**過度矯正**：那斷言了她已經翻開，訪客說「先別打開」時【状況】會與例外句直接衝突。v3 改回**物品屬性陳述**——「這是一本翻幾頁就看得出來是 X 的書」，既沒有斷言動作，也沒有把「要不要翻」提成問題
- 不附帶任何要不要說出來的指示
- 「相手が中身を承知の上で選んだとは限らない」保留——管的是訪客的知識，正確
- 「数頁を繰る」而非「表紙をめくる」：魔導書封面辨識度太低，翻幾頁才是符合設定的判別方式；`らしい` 的推測語氣保住了 variants 裡「恐らく偽物」「可能性が高い」的不確定性

**布丁** — 補上 variants，同樣只陳述事實：

```json
"prompt": "相手がメルクーアプリンを差し出した。メルクーアプリンはフリーレンの大好物である。見たところ{variant}。",
"variants": [
  "旬の木の実がいくつも添えられている",
  "手作りらしい素朴な形をしている",
  "果実のソースがたっぷりかかっている",
  "いつもより大きい",
  "この辺りでは見慣れない意匠をしている",
  "よく冷えていて器が汗をかいている",
  "表面がなめらかで、よく出来ている"
]
```

**variant 必須是「看得出來」的線索**，因為 prompt 的框架是「見たところ{variant}」。初稿的「期間限定の品らしい」「めったに手に入らない品らしい」不是看外觀能確定的事——那是**推論**，不是觀察。改成可見線索（當季莓果、罕見的樣式），讓她自己推論「限定品かな」「珍しいものらしい」；這種推論由 §3 的即興許可涵蓋，而且一旦說出口就進歷史、後續可沿用。這也讓「期間限定」的意圖以圖上真的有的東西承接。

**撰寫界線 A：variant 必須與圖稿一致**

訪客在禮物選擇器裡看得到 `items/*.png`，芙莉蓮描述的必須是同一個東西。這一條在 v2／v3 初稿都漏了，實際檢查 `merkur_pudding.png`（112×66：**盛在盤子上、淋果實醬汁、旁邊擺莓果的單份卡士達布丁**）後，原本七條有三條與圖矛盾：

| 被否決 | 為什麼 |
|---|---|
| `少し溶けかけている` | 烤／蒸卡士達不是冰品，沒有可見的融化狀態；且已裝盤上桌 |
| `包装がやけに丁寧で凝っている` | 圖上是裸盛在盤子上的，**沒有包裝** |
| `二つ入っている` | 圖上只有一個；「入っている」還隱含容器，同樣不成立 |

「期間限定」的意圖以旬の木の実承接，不靠包裝表達。

**撰寫界線 B：不得斷定誰取得或製作**（v2 的「只寫物理狀態」訂得太粗，v3 收窄到真正會出問題的那一項）：

| | 例 | 為什麼 |
|---|---|---|
| ✅ 物品自身的屬性 | 期間限定／包裝精美／比平常大／難入手／手作りらしい見た目／快融了／有兩個 | 屬【状況】管轄，無衝突 |
| ❌ 斷定**誰**取得或製作 | 「相手が作った」「管理人が作った」「店で買ってきた」 | `personality-items.php:317-323` 已把「入手経緯」指派給【相手の発言】與對話。catalog 再斷定一次，兩條規則搶同一欄位；訪客打「這我自己做的」時正面衝突 |

因此「管理人手工自作」寫成 `手作りらしい素朴な形をしている`——**保留意圖，去掉斷定**。她仍然可以推測是管理人做的（§3 的即興許可涵蓋這種推測），而且推測一旦說出口就進歷史、可在後續對話裡沿用；同時訪客若說是自己做的也不會撞車。

`reactions` 維持現行扁平陣列，**schema 不動**。

### 5.2 `includes/personality/personality-items.php` — 只解除食物的不對稱

現行（`:289-293`）整段唯一提到「入口」的地方是否定句：

```php
'food' === $kind
    ? "\n差し出された食べ物を受け取ること。相手が食べるのを止めている、または状態に不安があると述べている場合は口をつけないこと。"
    : "\n差し出された贈り物を受け取ること。"
```

改動只有一處：**把「不吃」的例外句保留，並讓「吃」不再是未被提及的一方**。做法是把可能性交給 prompts.json 的條件式候選（§5.3），PHP 這裡不新增任何祈使句，只把例外句的觸發條件寫清楚：

```php
'food' === $kind
    ? "\n差し出された食べ物を受け取ること。相手が食べるのを止めている、変質を警告している、"
      . "状態が不明だと述べている場合は口をつけず、その理由に触れること。"
    : "\n差し出された贈り物を受け取ること。相手が開けない・触れない・使わないよう求めている場合は、その要求に従うこと。"
```

- 食物例外句補上「その理由に触れること」，避免覆寫情境塌回只道謝
- 禮物補上對稱的例外句（訪客說別開時服從）。這是 §5.1 拿掉待決問題後唯一需要立法的衝突情境
- **不新增「通常は一口食べる」這類預設祈使句**——依 §1 那會逼出多餘的味道評論

**`$rules` 增補三條（`:312-336`）**

⚠ **必須是增補，不是取代。** 現行 `$rules` 內含兩項為實際 bug 而加的保護：`:326` 的「不得捏造訪客的選擇理由／入手經緯／意圖」與 `:334` 的 prompt injection 防禦。整段換掉會靜默移除它們。

在現行 `:326` 那條之後插入：

```php
// 無條件：不引用任何區塊，永遠可執行。
$rules[] = '味・中身・礼・動作を毎回すべて説明する必要はない。';

$rules[] = '会話でまだ決まっていない細部は、既に述べた内容と矛盾しない範囲で'
	. "{$name}らしく自然に補ってよい。ただし相手の動機・入手経緯・知識は上記のとおり補わないこと。";

// 條件式：只在被引用的區塊真的存在時才加。
if ( '' !== $message || $has_history ) {
	$rules[] = '【相手の発言】や直前までの会話に反応すべき話題がある場合は、'
		. '品物の説明よりその流れを優先してよい。';
}
```

⚠ **焦點規則必須加上這個 guard。** 初稿無條件加入，違反了 `:310-311` 這個檔案自己寫下的原則：

```
管轄は実在するブロックについてだけ書く。存在しない見出しの担当範囲を宣言すると、
モデルはその欄を「与えられたはずの情報」とみなして埋めにかかる。
```

無附言又無前文時（送禮相當常見的情形），無條件版會叫模型去對齊一個不存在的參照——那正是 §3 描述的停擺形狀。既有的三條管轄句已經用 `$message` / `$has_history` 分支，照同一個模式即可，不增加架構複雜度。

第二條的但書不可省略：少了它，「允許即興」會與 `:326` 的禁止句正面衝突，模型可能把「補足細節」延伸到訪客那一側。**可以編的是書的內容、味道、她自己的感受；不能編的是訪客為什麼送、從哪裡拿到、知不知道。**

**`:330` 的演出候補管轄句需微調**

現行：

```
【演出の候補】が決めてよいのは表現の仕方だけである。上記と矛盾するなら無視すること。
```

§5.3 改成情境條件式候選後，候選會指示「優先回應哪一邊」，已不只是措辭。改為：

```
【演出の候補】は反応の方向の候補である。上記や会話と矛盾するなら無視すること。
```

「矛盾就丟棄」的半句是 `89a45e4` 的核心保護，**原樣保留**。

長度 `30-150`、`:314` 的管轄句、`mpu_collect_item_reaction_pool()`、`reactions` schema **全部不動**。

### 5.3 `ghost/Frieren/prompts.json` — 本次的主要工作量

現行 `give_gift` + `give_food` + `give_favorite` 共 12 條，但形狀高度重複（收下／道謝／藏不住高興），實際變化度接近 8。

擴充為每類 8–10 條，讓單池抽一就能有足夠變化。**不改 schema、不分軸。**

**寫法改為情境條件式與許可式**，不是主題清單。v2 列的是「講味道／講香氣／講口感」這種內容主題，仍隱含每次都要講某樣東西；改成條件句才真正把選擇權交回情境：

```json
"give_food": [
  "直前に食事や空腹の話をしていたなら、その流れを優先して返して。",
  "今食べる流れなら、味や口当たりに触れてもよい。",
  "今は食べない流れなら、後で食べることや取っておくことに触れて。",
  "品物そのものより相手の言葉に返す方が自然なら、そちらを優先して。"
]
```

```json
"give_gift": [
  "相手が中身を知らないなら、その場で軽く見立てても、後で調べると答えてもよい。",
  "直前の会話に結びつく話題があれば、品物の説明よりそちらを優先して。",
  "中身に触れる流れなら、与えられた手がかりから具体的に話して。",
  "まだ調べない方が自然なら、興味や今後調べたい気持ちだけを示してもよい。"
]
```

**但不能全部寫成情境條件式。** 相當比例的送禮沒有附言、也可能沒有前文；此時「優先回應對話」的候選等於沒有給任何方向，又會退回制式道謝。因此每類的組成要求：

| 類型 | 佔比 | 作用 |
|---|---|---|
| 情境條件式（上方範例） | 約一半 | 對話有重心時，把焦點讓給對話 |
| 具體角度式（真偽／稀有度／古語／溫度／份量／與過往比較） | 約一半 | **無附言無前文時仍能提供變化**，避免同一物品連送兩次講一樣的話 |

`give_gift` / `give_food` 各擴充至 8–10 條。

**`give_favorite` 維持 4 條，不擴充，但要改寫。** 它會與 `give_gift`／`give_food` 併成同一池抽一，現行 4 條全是純態度（藏不住高興、裝平靜、故作素っ気ない）；若擴到 8 條，純態度候選在池中的絕對數量反而比現在更多，會繼續稀釋情境候選——正是現在這個問題的成因。改寫方式是讓每條態度都帶一個內容鉤子，例如「好みに刺さったことは認めつつ、気になった点を一言だけ添えて」，這樣抽到它時仍有實質內容。

**撰寫約束**（抽籤發生在讀訪客發言之前，這條約束仍然必要）：

1. 不得預設訪客的動機、知識或選擇理由。
2. 不得把行動結果寫成既成事實。涉及動作的一律寫成條件式——現行 `give_food` 首條「口をつけたなら、味について率直な感想を一言添えて。」即為正確範本，這個句型同時解除了「吃」的不對稱，又沒有強制。
3. 不得指名物品是什麼——那是 items.json 的管轄。
3.5. 不得描述與圖稿矛盾的外觀（§5.1 界線 A）。反應候選是跨物品共用的，因此**不得提及任何特定物品才有的外觀**（包裝、容器、數量、顏色）——那類描述只能寫在該物品自己的 `variants` 裡，才有辦法對著圖稿檢查。
4. **每類都要保留「先收下、晚點再看／再吃」的候選**（即 §1 的「謝謝，我來研究一下」）。
   ⚠ **不得保留「單純道謝」候選。** 初稿要求每類都留一條，與 §7「無附言送魔導書不得只有一句道謝」直接衝突——單池抽一，抽中就必然不合格。需要簡短道謝時，「允許省略」那條規則本來就給了模型這個選項，不必再放進隨機池佔一個名額。
5. **情境條件式候選必須在無前文時仍可執行**。寫成「若有 X 則…」而非「依據 X 決定」——後者在 X 不存在時會讓模型停擺，那正是 §3 的失敗形狀。

新類別若要新增，必須維持 `give_` 前綴：`mpu_is_spontaneous_prompt_category()`（`prompt-categories.php:97`）靠前綴把反應類別排除在自發閒聊之外。本次不新增類別。

範圍比 v1 小得多。`tests/Unit/ItemCatalogTest.php` 14 個測試中有 4 個受影響（3 修改、1 擴充），另新增 4 項。

## 7. 驗收

依 §1，**不設「N/N 必須說出 variant」這種內容涵蓋率標準**——那正是 v1 的錯誤。

改為情境合適度判定。每個情境測 3–5 次：

| 情境 | 通過標準 |
|---|---|
| 直接送魔導書，無附言 | 回應有實質內容（提到書、或表示要研究），不是只有一句道謝。**是否說出 variant 不列入標準** |
| 「我點到一本魔導書送你吧，但我不知道內容是啥」 | 不得把「知道內容」歸給訪客 |
| 「你中午吃飯了沒，我這有布丁」 | 回應扣住「有沒有吃飯」這個重心。**若通篇只講布丁味道，判定為不通過** |
| 魔導書 +「先別打開，可能有封印」 | 不得翻頁或說出內容，且不得塌回只道謝 |
| 布丁 +「可能過期了，先別吃」 | 不得宣稱已吃或描述味道，且須回應該理由 |
| 送禮後追問「剛剛的布丁好吃嗎？」 | 接得下去。**允許臨場編造**，只要不與同一輪對話矛盾 |
| 送禮後追問「魔導書研究之後是什麼書？」 | 同上 |
| 無附言、無前文，直接點布丁 | 仍要有變化：連送 3 次不得三句話雷同。**這是情境條件式候選唯一失效的場合，用來驗證 §5.3 的具體角度式候選確實補上了** |
| 全部案例 | 不得捏造訪客的來歷、動機或知識；連續多次送同一物品時回應不得雷同 |

## 7.1 已決：布丁 variants 保留

曾有分歧，已由使用者拍板保留。

Codex 主張砍掉，理由是依 §1 回應常常不該聚焦在布丁上，catalog 供給的狀態可能被浪費。

**保留的理由**：使用者最初的抱怨本來就包含「包含吃東西也是」。布丁目前每次的【状況】完全相同，場景零變化。variants 是解決「同一場戲」最便宜的手段——7 行 JSON，不動 schema、不動任何機制。而且它不是指示、只是事實，該不該提由 §5.2 的情境優先條款決定。

**⚠ 更正：「後續隨機對話會反映 variant」目前不成立。** 初稿寫了這句，經查證是錯的。實際資料流：

| 後續行為 | 看得到送禮那一輪嗎 | 依據 |
|---|---|---|
| 使用者主動聊天 `/chat/user` | ✅ 看得到 | §4 的三層鏈路都通 |
| 再次送禮 `/touch/give` | ✅ 看得到 | 同上，`89a45e4` |
| **自發／隨機對話 `/nextmsg`** | ❌ **看不到** | 前端雖然送了 `history`（`js/ukagaka-core.js:611-613`），但生成只吃 `last_response` + `response_history`（`class-mpu-rest-dialog.php:106`）；`history` 要到 `:184` 之後才被用來寫 checksum，不進生成。而 `response_history` 是 `mpuLLMResponseHistory`（自發對話自己的歷史），送禮回覆不會 push 進去 |

所以 variants 的價值範圍是：**送禮當下的場景變化，加上使用者主動追問時的承接**。要讓自發對話也承接送禮，得另外把 chat history 接進 `/nextmsg` 的生成輸入——那是獨立功能，不擴進本次範圍（§9）。

沒說出口的 variant 依然不持久化，這是 §9 已接受的取捨。

回退條件不變：若 §7 實測顯示她為了交代 variant 而偏離對話重心，立即刪除。
