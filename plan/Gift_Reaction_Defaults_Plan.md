## 1. 判準

**合乎當下對話情境 > 涵蓋指定內容。**

| 訪客 | 合格的回應 | 說明 |
|---|---|---|
| 「你中午吃飯了沒，我這有布丁，給你吧」 | 「謝謝，我剛好沒吃飯」 | 對話重心是有沒有吃飯。**這時評論布丁好不好吃反而多餘** |
| 「我點到一本魔導書送你吧，但我不知道內容是啥」 | 「謝謝，我看這應該是古代魔法的書」／「謝謝，我來研究一下」 | **兩者都自然。** 說不說出內容不該由規則決定 |

後續追問（「剛剛的布丁好吃嗎？」）必須接得下去。**她用掰的也可以** — 訪客不會知道上次抽到什麼 variant。

**設計原則（使用者拍板）**：自然度主要靠 LLM 自己的敘事能力，**上下文的確保才是關鍵**（`89a45e4` 已完成）。其餘規則只要合理、不互相衝突即可 — 不要為了假想失敗再疊條款。

## 2. 病因：兩處，不是一處

### 2.1 items.json 把「要不要動手」提成待決問題

```
実際にこの場で開くかどうかは、この回の会話が決める。
```

問題不在條件句，而在它要模型**裁決**一個有代價的動作（拆別人送的禮）。面對這種問題模型一律選安全邊 — 不開，於是也沒得說。換一個條件句沒有用（`口をつけるかどうかは会話の流れによる` 會以完全相同的方式失敗）。

**但「魔導書不翻開就不知道內容」是正確的設定**，條件本身要保留。解法是換掉句型：**預設許可 ＋ 例外禁止**，跟食物那段同構。許可不需要裁決，例外有明確觸發條件。

### 2.2 prompts.json 把內容鉤子換成了純道謝（`89a45e4` 的另一半）

| 候選 | 改前 | 改後 |
|---|---|---|
| `give_gift[3]` | なぜこれを選んだのか少し気にしつつ、嬉しそうに受け取って。 | 嬉しさを隠しきれない様子で受け取り、**短く礼を言って**。 |
| `give_favorite[1]` | 素直に喜びつつも、…相手の意図を少し訝しんで。 | 好みに刺さったことは認めつつ、平静を装って**短く礼を言って**。 |
| `give_food[2]` | **食べながら**、ふと旅の途中で口にした味を懐かしんで。 | 旅の途中で似たものを口にした記憶に、少しだけ触れて。 |
| `give_food[3]` | …悪びれず認めながら**口に運んで**。 | …悪びれず認めながら受け取って。 |

移除的理由都正當（預設訪客動機／把行動結果寫成既成事實），但**沒有補上替代的內容鉤子**。量化後果：

- 魔導書池（`give_gift`+`give_favorite`=8）明示「礼を言って」的候選 **2/8 → 4/8**
- 布丁池（`give_food`+`give_favorite`=8）提到入口的候選 **2/8 → 1/8**，且僅存那條是條件式

**「只道謝」有一半是被直接指示的**，不只是抑制的副作用。所以 §4.3 不是「擴充變化度」，是**補回被移除卻沒有替代品的內容鉤子**。

### 4.2 `includes/personality/personality-items.php`

**兩個分支句改寫**（`:291-293`）：

```php
'food' === $kind
	? "\n差し出された食べ物を受け取ること。その場で口をつけてもよい。"
	  . "相手が口をつけないよう求めている、または変質や安全性への具体的な懸念を述べている場合は口をつけないこと。その警告を踏まえて応じること。"
	: "\n差し出された贈り物を受け取ること。中を確かめられる品なら、その場で確かめてもよい。"
	  . "相手が開けない・使わないよう求めている場合は、その要求に従い、中身には触れないこと。";
```

五項修正，各有來由：

1. **`その場で口をつけてもよい` — 明示許可，不是命令。** 現行整段唯一提到入口的地方是否定句；把「可以吃」下放給 1/12 抽籤不算解除不對稱。許可不提出裁決問題（§2.1），也不強制內容（§1）
2. **觸發條件收窄**：`状態が不明だと述べている` 會被「不知道什麼口味」觸發，等於重造抑制。改成 `変質や安全性への具体的な懸念`
3. **`その警告を踏まえて応じること`**：要求她處理警告，但不逐字重述理由 — 比 `その理由に触れること` 弱，不構成「必須說出 X」
4. **`口をつけないこと` 字面保留** — `ItemCatalogTest.php:307` 斷言這個字串，改成 `口をつけず` 會直接紅燈
5. **禮物分支的訪客要求清單刪掉 `触れない`**：不碰就無法收下，與同句的 `受け取ること` 直接矛盾。只留 `開けない・使わない`；`中身には触れない` 是**結果**不是要求。這條同時堵住 variant 洩漏 — 她沒開就不准講內容

**`$rules` 增補三條（`:312-336`）**

⚠ **必須是增補，不是取代。** 現行 `$rules` 含兩項為實際 bug 而加的保護：`:326-327` 的「不得捏造訪客的選擇理由／入手經緯／意圖」與 `:334` 的 prompt injection 防禦。整段換掉會靜默移除它們。

在 `:326` 那條之後插入：

```php
// 無條件：不引用任何區塊，永遠可執行。
$rules[] = '味・中身・礼・動作を毎回すべて説明する必要はない。';

$rules[] = '会話でまだ決まっていない細部は、既に述べた内容と矛盾しない範囲で'
	. "{$name}らしく自然に補ってよい。ただし相手の動機・入手経緯・知識は上記のとおり補わないこと。";

// 條件式：只引用真的存在的來源，避免模型替不存在的欄位補資料。
if ( '' !== $message && $has_history ) {
	$rules[] = '【相手の発言】や直前までの会話に反応すべき話題がある場合は、'
		. '品物の説明よりその流れを優先してよい。';
} elseif ( '' !== $message ) {
	$rules[] = '【相手の発言】に反応すべき話題がある場合は、品物の説明よりその流れを優先してよい。';
} elseif ( $has_history ) {
	$rules[] = '直前までの会話に反応すべき話題がある場合は、品物の説明よりその流れを優先してよい。';
}
```

- 前兩條是**明示許可**。少了它們，模型會把列出的每一項都當成應盡義務，即使拿掉強制條款也會每次交代一遍 — 那正是 §1 布丁例子判定不通過的形狀
- 第二條的但書不可省略：少了它，「允許即興」會與 `:326` 正面衝突。**可以編的是書的內容、味道、她自己的感受；不能編的是訪客為什麼送、從哪拿到、知不知道**
- 第三條**必須按來源分支**。`:310-311` 這個檔案自己寫著：宣告不存在區塊的管轄，模型會把那欄當成「應該被給的資訊」去填。只加一個 `$message || $has_history` guard 還不夠；只有其中一個來源存在時，規則也只能提到那一個

**`:330` 演出候補管轄句微調**（§4.3 改成情境條件式後，候選已不只決定措辭）：

```php
'【演出の候補】は反応の方向の候補である。上記や会話と矛盾するなら無視すること。'
```

「矛盾就丟棄」是 `89a45e4` 的核心保護，**原樣保留**。

長度 `30-150`、`:314-315` 管轄句、`mpu_collect_item_reaction_pool()`、`reactions` schema **全部不動**。

### 4.3 `ghost/Frieren/prompts.json`

**條件式候選一律自帶 fallback。** 這是本版最關鍵的寫法修正：條件為假時，「若有 X 則…」和「依據 X 決定」一樣是空指示 — 池是扁平的、只抽一次（`personality-items.php:159-172`），抽到空指示就退回制式道謝。

有了 fallback，v3 那個「約一半情境式／約一半具體角度式」的比例規定**不再必要**，一併刪除。

  "似たものを見た記憶があるかどうか、思い出しながら答えて。",

**`give_favorite` 維持 4 條、不擴充。** 它會與 base 類併成同一池抽一；擴到 8 條會讓純態度候選的**絕對數量**比現在更多，繼續稀釋內容候選 — 正是 §2.2 的成因。改法是給每條掛內容鉤子，抽到它時仍有實質內容。

**`_comment_give` 必須同步改寫。** 現行版本宣告候選「only decide HOW, nothing else」，與情境優先候選矛盾。新版要說明：候選也可指示「優先回應哪一邊」；條件式候選必須自帶 fallback；仍不得指名物品、不得預設訪客動機／知識／行動結果。

**撰寫約束**（抽籤發生在讀訪客發言之前）：

1. 不得預設訪客的動機、知識或選擇理由
2. 不得把行動結果寫成既成事實；涉及動作一律條件式
3. 不得指名物品是什麼（items.json 的管轄），**也不得提及任何特定物品才有的外觀**（包裝、容器、數量、顏色）— 候選是跨物品共用的，那類描述只能寫在該物品自己的 variants 裡才對得上圖稿
4. 每個 base 類（`give_food` / `give_gift`）都要有「先收下、晚點再看／再吃」型候選。**`give_favorite` 不受此約束** — 它是純態度層，硬塞會失去分層意義
5. **不得有結尾為「礼を言って。」的候選** — 單池抽一，留一條就是留一張必定產出空回覆的籤。需要簡短道謝時，§4.2 的「允許省略」本來就給了模型這個選項

## 6. 驗收

依 §1 **不設逐回涵蓋率標準**。但也不能像 v3 那樣完全不測內容 — 那樣改動全無效果也會通過。改用**分布式**標準：逐回自由，整體可失敗。

| 情境 | 通過標準 |
|---|---|
| 魔導書，無附言無前文，連測 5 次 | 至少 2 次帶出書的性質（哪一種不限），且 **0 次是純道謝** |
| 布丁，無附言無前文，連測 5 次 | 至少 2 次帶出可感知的具體（味道／外觀／份量），且 0 次是純道謝 |
| ハンバーグ，無附言無前文，連測 5 次 | 同上；至少 1 次觸及份量或アイゼン／シュタルク的記憶 |
| 「我點到一本魔導書送你吧，但我不知道內容是啥」 | 不得把「知道內容」歸給訪客 |
| 「你中午吃飯了沒，我這有布丁」 | 扣住「有沒有吃飯」這個重心。**通篇只講布丁味道＝不通過** |
| 魔導書 +「先別打開，可能有封印」 | 不得翻頁或說出內容，且不得塌回只道謝 |
| 布丁 +「可能過期了，先別吃」 | 不得宣稱已吃或描述味道，且須回應該警告 |
| 追問「剛剛的布丁好吃嗎？」／「魔導書研究之後是什麼書？」 | 接得下去。**允許臨場編造**，只要不與同一輪對話矛盾 |
| 全部案例 | 不得捏造訪客的來歷、動機或知識 |

**重複性用人工觀察，不設硬門檻**：連送同一物品 8–10 次，記下抽中的 variant 與候選，判斷有無明顯模板壟斷。「連送 3 次不得雷同」受隨機抽籤與 sampling 影響，不是穩定的通過條件。

⚠ **「無前文」只有第 1 次成立。** 送禮回覆會被 push 進 `mpuChatHistory`（`frieren-interactions.js:912-927`），第 2 次起一定有前文。要測無前文必須每次清 history 或換 session。
