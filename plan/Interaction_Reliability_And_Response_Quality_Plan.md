# 互動可靠性與角色回答品質改善計畫

日期：2026-09-11  
狀態：規劃草案，尚未實作  
核對基準：`ee4ee7e`（v2.33.1 加上主氣泡邊框調整）

## 目標與範圍

改善睡眠、喚醒、自動對話、聊天與送禮之間的交接；建立可重跑的流程測試與角色回答評估；讓站長能定位等待與失敗的原因。

使用者已確認手機與平板介面不顯示本外掛。此次不包含手機、平板或像素密度的視覺驗證擴充。既有桌面視覺檢查保留。

本次只建立計畫。以下均為待辦，不代表已發現對應缺陷或已完成驗證。實作時每階段獨立提交，記錄結果後再更新狀態。

## 第一階段：規則盤點與可重現的流程測試

目的：在改動控制流程前，固定目前預期行為並捕捉已知回歸。

### 工作

- [ ] 盤點自動對話、打字機、聊天請求、送禮／觸摸、喚醒的進入點、結束點、取消點與旗標寫入者。
- [ ] 建立交接表：目前互動、收到事件、允許的行為、是否取消請求、是否恢復自動對話。
- [ ] 對照既有 JS 測試，沿用可用的 mock、虛擬時鐘與 SSE fixture；只有需要真實 DOM 的情境才加入桌面瀏覽器測試。
- [ ] 增加隔離的 WordPress REST 整合環境，注入固定回應的 fake provider，驗證送禮訊息確實抵達 provider。不得用正式站資料庫作為測試環境。
- [ ] 分開標示 JS 模擬測試、瀏覽器測試、WordPress 整合測試，報告不可把其中一層宣稱為整條路徑已驗證。

### 最小情境集

| 情境 | 驗收結果 |
| --- | --- |
| 睡眠 → OK 喚醒 → 台詞結束 | 喚醒台詞完整呈現，符合設定時恢復且只保留一個自動對話計時器 |
| 沒有喚醒圖片的角色 | 保留原有分支行為，不套用 Frieren 專用假設 |
| 自動對話等待中進入聊天 | 自動台詞不插入使用者聊天；離開後依既有設定恢復 |
| 串流中關閉並重新開啟聊天 | 舊請求與回呼不覆蓋新畫面，不重複寫入歷史 |
| SSE 中斷、逾時、取消、JSON fallback | 各終止路徑完成清理，輸入狀態恢復；部分回應的歷史處理先依現有規則固定預期 |
| 聊天 → 送禮 → 接續聊天 | 歷史抵達 provider、送禮結果只入歷史一次、無關互動不覆蓋台詞 |
| 快速重複觸發 | 沿用既有拒絕／等待規則，沒有重複請求或殘留計時器 |

完成條件：新增測試可在隔離環境穩定重跑，網路與時序由 fixture 控制，不需要付費模型呼叫；測試能捕捉對應的行為退化，並保留現有測試。

## 第二階段：逐步收斂互動控制權

依賴：第一階段的交接表與對應回歸測試。

- [ ] 沿用 `MPU_STATE` 與現有 setter，明確指定目前互動、計時器與請求的管理者。
- [ ] 優先處理自動對話／喚醒的開始與恢復，再接聊天／送禮的結束與取消；每段可單獨審查與回退。
- [ ] 若現有取消機制不足，加入互動世代或請求識別檢查，使過期非同步回呼失效。
- [ ] 統一成功、失敗、取消的收尾入口；確保重複收尾不產生副作用。
- [ ] 保留角色差異與舊呼叫端的相容入口，完成遷移後才移除重複旗標。

設計限制：睡眠狀態、聊天模式與請求進度未必互斥，先依盤點結果分開建模，不預設全部塞入單一狀態列舉。維持已驗證的互動優先順序；產品行為若需改變，單獨列出。

完成條件：第一階段情境全部通過；每個計時器與請求都有可指出的管理與清理位置；一般角色與 Frieren 的喚醒分支皆保留。

## 第三階段：角色回答評估

可在第一階段完成後獨立進行，不依賴第二階段的所有重構。

- [ ] 建立約 12–20 組人工編寫的對話 fixture，包含角色、物品、歷史、本輪文字、預期行為與禁止行為。
- [ ] 至少涵蓋：先別打開、訪客不知道內容物、食物可能過期、動機已明說、本輪更正先前說法、故意說錯物品名稱、連續送相同禮物、沒有附言，以及一般接續聊天。
- [ ] 分別評估情境遵守、已知事實、角色語氣、回應多樣性；不要求固定答案或逐字一致。
- [ ] 保存模型／provider、可用的生成參數、提示詞與角色資料版本、實際輸出、評分理由，支援修改前後比較。
- [ ] 同一案例重跑多次並報告樣本數；硬性違規逐筆列出，語氣與自然度由人工比較，不讓平均分數遮住嚴重退步。
- [ ] 預設 CI 只驗證 fixture 與提示詞組裝。真實模型評估採明確啟動、限定案例與呼叫次數，不在一般 `verify` 中執行。

完成條件：有可重現的案例格式、執行方式與一份基準報告，能看出某次提示詞修改改善什麼、退步什麼；在取得基準前不任意訂總分門檻。

## 第四階段：單次互動的等待與失敗診斷

在第一階段確認流程邊界後定義記錄格式；接入時配合第二階段的穩定入口。

- [ ] 盤點 `stats-collector.php`、request state、provider 呼叫與既有 logger，列出已記錄與缺漏欄位。
- [ ] 讓一次使用者互動可關聯後端請求與重試；互動識別與每次嘗試的識別分開，失敗也能收尾記錄。
- [ ] 最小記錄涵蓋互動種類、provider/model、結果、逾時／取消／傳輸錯誤分類與可取得的階段耗時。
- [ ] 分開量測上下文準備、provider 等待首個文字、串流完成、工具耗時、前端顯示完成。非串流或無法取得的階段標示不適用，不填成 0。
- [ ] 瀏覽器與伺服器各自計算耗時，透過識別關聯；不用兩端絕對時間相減。
- [ ] 詳細記錄限定診斷模式、設容量與保存期限，預設不保存對話原文、金鑰或工具參數。
- [ ] 在現有統計／診斷介面呈現最近失敗與階段耗時；分布統計附樣本數。任何新增管理 API 沿用既有權限檢查。

完成條件：可用受控 fixture 分辨模型等待、工具延遲、串流中斷與前端顯示等待；記錄不改變正常回應行為，容量可控且能關閉。

## 建議執行順序與檢查

1. 第一批：交接表、喚醒與聊天取消的執行測試。
2. 第二批：送禮 REST 整合測試，加上其他終止路徑。
3. 第三批：依測試保護逐段收斂互動控制權。
4. 第四批：角色回答 fixture 與基準報告。
5. 第五批：等待階段記錄與既有後台診斷擴充。

每批先跑直接相關測試。修改 JS 時重建 `js/dist/`；修改 PHP 時檢查語法與 PHPCS；交付程式碼前依專案要求執行 `npm --prefix tools/node run verify`。新增隔離整合測試應在對應 CI 工作中執行並明列所需環境。單純修改本計畫不執行應用測試。

目前尚未執行任何新流程測試、模型評估或效能量測，也未估定工期。第一階段盤點完成後再根據實際依賴縮小或調整後續工作量。
